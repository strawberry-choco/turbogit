*separate bundle namespaces*, separate tab roots, separate action families, and
separate failure strings, they are not one feature with two names.

### Topology

**The conceptual model, stated by the docs and confirmed by the bundle's split
namespaces:**

| | Shelf | Stash |
| --- | --- | --- |
| Who produces it | "Patches with shelved changes are generated by IntelliJ IDEA" (shelving:16) | "Stashes are generated by Git" (shelving:14) |
| Granularity | "you can select **some** of the local changes instead of shelving them all" (shelving:17) | "stashing involves **all** uncommitted changes" (shelving:17) |
| Usable outside the IDE | no, "applied through the IDE" (shelving:16) | yes, "can be applied from within IntelliJ IDEA, **or outside it**" (shelving:14) |
| Unversioned files | "You cannot shelve unversioned files" (shelving:32) | not stated either way |
| Root node title | `Shelves` (VcsBundle:1306) | `Stashes` (GitBundle:459) |
| Tab title | `Shelf` (VcsBundle:542) | `Stash` (GitBundle:458) |
| Action family | `Vcs.Shelf.*` (5 actions) | `Git.Stash.*` (9 actions) |
| Reusability | "Once shelved, a change can be applied as many times as you need" (shelving:33) | "A stash can be applied as many times as you need to any branch" (shelving:246) |

**Both are tool-window tabs** next to Commit, in the same tool window
("The stashed changes will be moved to the **Stash tab next to the Commit tab** in
the same Commit tool window", shelving:263), and they **can be merged into one**:
"you can combine the Stash and the Shelf tabs into one … Enable the **Combine
stashes and shelves in one tab** option" (shelving:21-25). Bundle:
`settings.enable.stashes.and.shelves=Combine stashes and shelves in one tab`. When
merged, the diff-preview empty-state title is `Stashes and Shelves` (VcsBundle:1291)
and the empty list reads `No stashes or shelves added.` (VcsBundle:1288).

**The Shelve Changes dialog** (shelving:39-168). Field/control order as documented:

1. **File list**. "All files in the list are selected by default. Deselect the
   files that you do not want to shelve" (shelving:40)
2. **Toolbar**: Show Differences (`⌘D`), Revert, Refresh Changes (`⌃F5`),
   Group By, Expand/collapse all (`⌃⌦+` / `⌃⌦-`, "not available in flat view"),
   and a **Changelist** selector, "The active changelist is selected by default"
   (shelving:73)
3. **Summary line under the files pane**, "shows statistics on the currently
   selected changelist, such as the number of modified, new and deleted files. This
   area also shows how many files of each type are shown, and how many of them will
   be shelved" (shelving:74). **A live "N of M will be shelved" counter.**
4. **Commit Message field** = the shelf name (shelving:76)
5. **Diff pane**, base vs the version about to be shelved, with Previous/Next
   Difference (`⇧F7`/`F7`), Jump to Source (`F4`), Compare Previous/Next File
   (`⌥←`/`⌥→`, "only available when there is more than one file"), a
   side-by-side/unified switch, and the full whitespace/highlighting option set
   (shelving:78-168)
6. Footer: `Shelve Changes`

**The Unshelve Changes dialog** (shelving:182-190), field order:

1. **Name**, "specify the changelist you want to restore the unshelved changes to.
   You can select an existing changelist from the list **or enter the name for a
   new changelist to be created**", one field, two roles
2. **Comment** (optional)
3. **Set active** checkbox
4. **Track context** checkbox
5. **Remove successfully applied files from the shelf** checkbox
6. Footer: OK

**The Stash dialog** (shelving:254-262), field order:

1. **Git root selector**, "select the appropriate Git root" (shelving:256)
2. **Current branch** readout (bundle: `stash.unstash.changes.current.branch.label=Current branch:` GitBundle:483)
3. **Message** field, bundle `stash.message=&Message:` with tooltip "Enter stash
   message here" (GitBundle:441-442)
4. **Keep index** checkbox, `stash.keep.index=Keep &index`, tooltip "If this
   checkbox is selected, all changes already added to the index are left intact"
   (GitBundle:439-440)
5. Footer: `Create Stash` (GitBundle:437)

Note the root-then-branch order: **the stash dialog is per-root**, and it *shows*
you which branch before you commit to it.

**The Unstash dialog** (`Unstash…` on a stash, shelving:279-282): `As new branch`
field, `Reinstate Index` checkbox, `Apply Stash` button. Bundle: `Git.Stash.UnstashAs.description`
= "Pop or apply selected stash as new branch with or without index", and
`unstash.branch.tooltip=If non-empty name is entered, the stash is checked out as a
new branch`, so an **empty name field is a valid state meaning "apply to the
current branch"**, not a validation error.

## UX, how it behaves

### How is it reached, and what hides behind a secondary affordance?

- **Shelve**: Commit tool window → right-click files *or a whole changelist* →
  `Shelve Changes` (shelving:37). Whole-changelist shelving is the primary path.
- **Shelve silently**: "select the file or changelist you want to shelve and click
  `Shelve Silently` on the toolbar or press `⌃⇧H`. **The name of the changelist
  containing the changes you want to shelve will be used as the shelf name**"
  (shelving:170). So silent shelving derives its name from the changelist, and
  "To avoid ending up with numerous shelves with the same name (such as `Default`,
  for example)…" (line 171), **the naming collision is a known, documented
  consequence of the silent path.**
- **Copy to a shelf without resetting**: "press `⌃⇧A` and look for the `Save to
  Shelf` action" (shelving:172) — `ChangesView.SaveToShelve`. **A third shelving
  verb that neither resets nor is named by the user.**
- **Stash**: Commit tool window → right-click → `Git | Stash Changes`
  (shelving:254). Also `Stash Silently` (`Git.Stash.Silently`) and
  `Stash Files` (`stash.files.action.text`, GitBundle:485).
- **Unshelve**: Shelf tab → select the changelist *or files* → `⌃⇧U` or context
  menu `Unshelve` (shelving:178-180). Silent variant `⌃⌥U`
  (`ChangesView.UnshelveSilently`).

Behind secondary affordances:

- **The shelf's whole lifecycle is drag-and-drop**: "drag a file or a changelist
  from the Commit tab to the Shelf tab … **wait for a second until it's activated**,
  and edit the new shelf name after releasing the mouse button" (shelving:171); and
  "You can also drag a file or a changelist from the Shelf tab to the Commit tab to
  unshelve it silently. **If you drag it holding the Ctrl key, it will be copied to
  the Commit tab but also kept in the shelf**" (shelving:192). **Two drag
  destinations, and a modifier that changes copy-vs-move.** The `⌃`-drag semantics
  are the whole undo story for a drag.
- **`Remove successfully applied files from the shelf` is a checkbox in the
  Unshelve dialog**, not a separate verb (shelving:187).
- **Restore of already-unshelved changes is behind a filter**: "Click `Show` and
  make sure that the **`Already Unshelved`** option is enabled … choose `Restore`"
  (shelving:204-208). Bundle: `shelve.show.already.unshelved.action=Already Unshelved`.
  So a hidden filter gates a recovery verb.

### Which verbs are destructive, and what do they confirm or preflight?

| Verb | Destructive | Confirmation | Evidence |
| --- | --- | --- | --- |
| Shelve (dialog) | no — changes are preserved | none needed | — |
| Shelve Silently | no | **none, by design** | shelving:170 |
| Unshelve | no, moves changes to a changelist | none | shelving:180-190 |
| **Unshelve and Remove** | **yes**, the shelf copy is destroyed | the same dialog; the checkbox is the disclosure | shelving:187; VcsBundle:1303 |
| **Delete** a shelf | **yes, irrevocably** | "right-click the changelist and choose `Delete` from the context menu or press `Delete`" (shelving:198), **no confirm documented** | shelving:198 |
| **Drop** a stash | **yes** | no confirm documented (shelving:283) | shelving:283 |
| **Clear** all stashes | **yes, all of them** | no confirm documented (shelving:283) | shelving:283 |
| Apply / Pop a stash | no / **yes**, Pop removes it | none documented; disambiguated by tooltip only (VcsBundle:1295) | VcsBundle:1295 |
| Revert inside the Shelve dialog | **yes**, "Revert all changes made to the local working copy of the selected files" (shelving:53) | inside a shelve dialog, so the commit is still safe | shelving:53 |
| Stash | no | none | — |
| Close the unstash-conflict state | n/a | notification offers `Resolve conflicts…` / `View saved changes…` | GitBundle:448-449 |

**Two destructive verbs carry no confirmation at all: shelf Delete and stash
Drop/Clear.** That is the finding. And the mitigations are structural rather than
dialogue-based:

- **Unshelve keeps the shelf by default.** "Remove successfully applied files from
  the shelf" is opt-in (shelving:187), so the default Apply/Pop pair on a *shelf* is
  `Unshelve` (keeps) with `Unshelve and Remove` as the separate, explicitly-named
  destructive sibling (VcsBundle:1301-1304). **The verb name carries the
  consequence**, "and Remove" is in the label.
- **Unshelved-but-removed files are recoverable from `Recently Deleted`**:
  "If you've deleted unshelved files by accident, you can view and restore them from
  the `Recently Deleted` node" (shelving:188), and they "will not be removed
  completely until deleted explicitly by selecting `Delete`" (line 187). **A shelf
  deletion is two-step: applied-then-marked, then explicitly deleted.**
- **Stash Apply keeps, Pop removes**, told apart only by tooltip
  (VcsBundle:1295) and by the doc's verbs (shelving:274-276).

### What can be undone, from where, and for how long?

| Undo | Reachable from | Lifetime | Evidence |
| --- | --- | --- | --- |
| Unshelve with `Restore` | Shelf tab → `Show` → enable `Already Unshelved` → select → `Restore` | "All unshelved changes can be reused **until they are removed explicitly by selecting Delete**" (shelving:202) | shelving:202-208 |
| Un-applied shelf files | `Recently Deleted` node (shelving:188) | until explicitly `Delete`d (shelving:187) | shelving:187-188 |
| Applied files left in the shelf | the shelf still holds them (default Apply) | indefinite, a shelf is not consumed by Apply | shelving:187 |
| `Save to Shelf` copy | the new shelf | indefinite; the working changes are untouched (shelving:172) | shelving:172 |
| `⌃`-drag from Shelf to Commit | the shelf copy remains | indefinite | shelving:192 |
| Stash after Apply | the stash remains in the list | indefinite | shelving:274 |
| **A stash lost to a failed unstash** | notification → `View saved changes…` | **until the user resolves and drops the stash**, see below | GitBundle:447-449 |

**The stash-unstash-conflict path is the sharpest undo case on this surface**, and
it is entirely in the bundle:

`stash.unstash.unresolved.conflict.warning.notification.title` = "Local changes were
restored with conflicts" (GitBundle:450), body:

> "Your uncommitted changes were saved to stash. Unstash is not complete, you have
> unresolved merges in your working tree. Resolve conflicts and drop the stash."
> (GitBundle:447)

with **two** actions: `Resolve conflicts…` (GitBundle:449) and
`View saved changes…` (GitBundle:448).

**Read that sequence carefully, the recovery instruction is "resolve conflicts
and drop the stash".** The stash is the *only* copy of the pre-update work, and the
app tells the user to delete it once the conflicts are handled. The doc states the
same from the other end: "This operation may fail if you have conflicts. This
happens because conflicts are stored in the index where you can no longer apply the
changes in their original state" (shelving:284). **So the stash is not a safe
backup once it has been popped into a conflicted index**, that is a real, citable
hazard, and a client must not present a popped stash as recoverable.

**Not undoable:** shelf `Delete`, stash `Drop`, stash `Clear`. All three are
terminal.

Remembered between uses:

- **Shelf location is a real, movable thing**: "click `Change Shelves Location` and
  specify the new location … If necessary, select `Move shelves to the new
  location`" (shelving:234-237). Bundle: `settings.change.shelves.location=Change Shelves Location…`
  and `settings.default.location=Default location is`. The stated motivations,
  avoiding accidental deletion when cleaning the working copy, and sharing shelves
  via a separate repo (shelving:231), are worth carrying.
- **Base revisions shelved for 3-way merge**: if enabled, "the base revision of
  files will be saved to a shelf that will be used during a 3-way merge if applying
  the shelf leads to conflicts" (shelving:226). **So shelving is also a mechanism
  for conflict recovery, not only for task-switching.** That is the third role of
  this surface and it is easy to miss.
- `Combine stashes and shelves in one tab` is persisted; the tab layout follows.
- The `Clean working tree using` setting (Shelve vs Stash) decides which mechanism
  Smart Checkout uses, see `02-branches-popup`.

## Flow, how tasks chain

### Entry points

1. Commit tool window right-click → `Shelve Changes` / `Stash Changes`
   (shelving:37, 254).
2. Commit tool window toolbar → `Shelve Silently` (`⌃⇧H`), `Stash Silently`,
   `Stash Files` (shelving:170; `Git.Stash.Silently`, `stash.files.action.text`).
3. `⌃⇧A` → `Save to Shelf` (shelving:172).
4. **Drag** Commit tab → Shelf tab (shelving:171).
5. Shelf tab → `⌃⇧U` / `Unshelve`; `⌃⌥U` for the silent variant (shelving:180, 191).
6. **Drag** Shelf tab → Commit tab; `⌃`-drag to copy (shelving:192).
7. Stash tab → row context menu: `Apply`, `Pop`, `Unstash…`, `Drop`; `Clear` for all
   (shelving:274-283).
8. Shelf tab → `Import Patches…` (`action.ImportIntoShelfAction.text`, VcsBundle),
   external patches arrive as shelves (shelving:214-218).

### Internal sequence, with dialog chaining

**Shelve with review:**

```
Commit tool window → right-click files or a changelist → Shelve Changes
  → Shelve Changes dialog                                          [dialog]
      file list (all selected)  +  "N of M will be shelved" summary
      toolbar: ⌘D show diff / Revert / ⌃F5 refresh / Group By / expand-collapse
      Changelist selector (active changelist)
      Commit Message  ← becomes the shelf name
      Diff pane (base vs about-to-shelve), ⇧F7/F7, F4, ⌥←/⌥→
  → Shelve Changes
  → the shelf appears in the Shelf tab
```

(shelving:37-168.)

**Task switch, the canonical journey, and it is a two-surface chain:**

```
dirty tree → need to switch branch
  → branch popup → Checkout → Smart Checkout
  → (this surface) shelve → checkout → unshelve            [cross-surface]
  → (conflict on unshelve) Conflicts dialog               [chained]
```

(manage-branches.md:107 + GitBundle:426-429.) The shelf is the mechanism Smart
Checkout uses, which is why `Clean working tree using: Shelve` is the default
setting (manage-branches.md:108).

**Stash with a message:**

```
Commit tool window → right-click → Git | Stash Changes
  → Stash dialog                                                [dialog]
      Git root selector
      Current branch: (readout)
      Message
      [ ] Keep index
  → Create Stash
  → the stash appears in the Stash tab; the changes list empties
```

(shelving:254-263.)

**Unstash onto a new branch:**

```
Stash tab → stash → right-click → Unstash…
  → Unstash Changes in {root}                                     [dialog]
      As new branch:  (empty = apply to the current branch)
      [ ] Reinstate Index
  → Apply Stash
  → (conflict)  Unresolved-conflict notification                   [chained]
        "Local changes were restored with conflicts"
        [Resolve conflicts…] [View saved changes…]
  → (clean) branch created or changes applied
```

(shelving:279-284; GitBundle:445-450, 482.)

**External patch → shelf → work:**

```
Shelf view → Import Patches…                            → "Copies a patch file to the shelf"
  → select the patch file
  → the patch appears in the Shelf tab as a shelf
  → select it → Unshelve Changes
```

(shelving:214-218; VcsBundle `action.ImportIntoShelfAction.text=Import Patches…`.)

**Shelve-as-conflict-safety (the third role):**

```
[setting] Shelve base revisions of files under DVCS = on
  → base revisions of tracked files are saved to a shelf
  → later, unshelving onto a moved-on history uses the shelved base
    for a 3-way merge instead of searching project history
  → (if the setting is off) history is searched — "which may take a while"
    and "the revision that the conflicting shelf was based on may be missing
    (for example, if the history was changed as a result of the rebase operation)"
```

(shelving:226-227.) **This is a fix for a history-rewrite interaction**: after a
rebase, the base revision a shelf was created against may no longer exist, and a
shelved base is the only surviving copy.

### What happens next on success

- Shelve: the entry lands in the Shelf tab; the working changes are removed only if
  the user shelved the whole set.
- Stash: "The stashed changes will be moved to the Stash tab next to the Commit tab
  in the same Commit tool window" (shelving:263), same tool window, so focus can
  cross tabs.
- Unshelve: files appear in a changelist in the Commit tab, ready to commit
  (shelving:190).
- Unstash-as-new-branch: a new branch exists and is checked out; then
  `Apply Stash` (shelving:282).

### What happens next on failure, and how the user recovers

| Failure | Evidence | Recovery |
| --- | --- | --- |
| Unstash produced conflicts | `Local changes were restored with conflicts` + "Unstash is not complete … Resolve conflicts and drop the stash" (GitBundle:447, 450) | `Resolve conflicts…` or `View saved changes…` (GitBundle:448-449), **the stash must be resolved-and-dropped, not left** |
| Unstash before an update | `Uncommitted changes that were stashed before update have conflicts with updated files` (GitBundle:445) | the same notification pair |
| Stash failed | `Failed to stash {0}` (GitBundle:451) / `Failed to Stash Files` (487) | **UNVERIFIED**, no bundled recovery action. Re-tested against shelving-and-unshelving-changes + settings-version-control-git 2026-10-06: the only documented stash failure is the unstash-conflict path; a topic search found no dedicated stash page (`stash-changes.html` is 404) → needs runtime capture (R3) |
| Stash not permitted | `Cannot Stash Changes Now` (GitBundle:438) | **UNVERIFIED**, the reason is not given. Re-tested against shelving-and-unshelving-changes 2026-10-06: the page's only refusal is apply-time ("You cannot apply a stash to a 'dirty' working copy", line 250), which is a different gate → needs runtime capture (R3) |
| Shelve failed | `Could not shelve local uncommitted changes:` (GitBundle:346) | the templated pair names shelf vs stash |
| Auto-save before a failed operation failed | `Could not save uncommitted changes on {0}` (GitBundle:424); and the after-the-fact `Before {0} your uncommitted changes were saved to shelf.` (413-414) | the changes are still in the shelf, so recovery is manual |
| Stash feature disabled | `Enable and view Git stashes` (GitBundle:491) | the link enables it |
| Shelve of unversioned files | "You cannot shelve unversioned files" (shelving:32) | the file must be added first |

### Escape / dismiss semantics

- The Shelve dialog is cancellable with no loss, nothing has moved yet.
- **Drag is the risky dismiss**: a completed drag has already moved or copied the
  changes, and the `⌃` modifier decided which (shelving:192). There is no undo
  prompt after the drop.
- **A conflicted unstash has no cancel**, the notification's only exits are
  resolve-then-drop or view-the-saved-changes (GitBundle:448-449). The pre-unstash
  work is now in the working tree *and* in the stash, and the app's stated
  resolution deletes the stash.
- `Unstash…` with an empty `As new branch` is a valid submit, not a validation
  error (`unstash.branch.tooltip`).

## Divergences (intentional)

| Dimension | Rebased behaviour | TurboGit behaviour | Why |
| --- | --- | --- | --- |
| UI | **Two separate tabs**, mergeable into one via a setting (shelving:21-25) | `CommitSubTab::{LocalChanges, Shelf, Stash}` with the Shelf and Stash panes as labelled placeholders per ADR-0008 (`crates/turbogit-ui/src/ui/commit_window.rs`) | The tab set already matches; only the panes are unimplemented. **This is the largest single implementation gap in the surface**, see ticket 10. The merge-into-one option is a small follow-on. |
| UI | Shelf `Drop` is labelled `Delete`; stash `Drop` is labelled `Drop` (VcsBundle:1299 vs `actions-labeled.tsv`) | — | An inconsistency, not a design. Deliberately **not** copied: TurboGit should use one verb per mechanism with an explicit object. Recorded so the divergence table is honest about a place where the reference is self-contradictory. |
| UX | Shelving selects *some* changes; stashing takes *all* uncommitted changes (shelving:17) | `Operation::Shelve { changes: Vec<Change>, message }` runs `git stash push` then discards the chosen paths (`operation.rs`) | TurboGit already models partial selection. The divergence is in the *mechanism*: TurboGit achieves a partial set by stashing everything then discarding the rest, which is correct but means the stash entry contains work the user did not ask to shelve. Rebased writes a real patch. Documented as a mechanism difference; the user-visible outcome matches. |
| UX | Shelving is also the **conflict-safety mechanism**, base revisions are shelved for later 3-way merges, which is the only way to survive a rebase that removed the base (shelving:226-227) | Not implemented | **Open gap and a real risk**: after a history rewrite, a TurboGit shelf's base may no longer exist. Worth copying; see ticket 11. |
| UX | Unshelve keeps the shelf by default; the destructive variant is a separately-named verb (`Unshelve and &Remove`, VcsBundle:1303) | `Dialog::Stash` has `Stash` / `Pop latest` / `Cancel` (`crates/turbogit-ui/src/ui/dialogs.rs`) | TurboGit's naming already carries the consequence (`Pop` vs `Stash`). Parity holds. |
| UX | Unshelved-then-removed files stay recoverable in `Recently Deleted` until explicitly deleted (shelving:187-188) | **No equivalent, verified in the codebase 2026-10-06**: TurboGit has no unshelve verb at all (zero matches for `unshelve` across `turbogit-app`, `turbogit-services`, `turbogit-ui`); the shelf is a single in-memory `Vec<Shelf>` (`crates/turbogit-app/src/state.rs:1041`) persisted to `.turbogit/shelf.ron` (`crates/turbogit-services/src/shelve_stash.rs:41-44`), whose only mutation found is `shelves.push` (`crates/turbogit-ui/src/ui/dialogs.rs:1042`) | **Open gap**, and it is what makes an unconfirmed shelf `Delete` survivable. See ticket 12. |
| UX | Shelf `Delete` and stash `Drop`/`Clear` carry **no confirmation** (shelving:198, 283) | `PendingConfirm` exists for destructive work elsewhere | Deliberate departure: TurboGit confirms terminal deletions. The reference relies on the two-step `Recently Deleted` safety net that TurboGit would also need; confirming is cheaper and consistent with the rest of TurboGit. |
| UX | A conflicted unstash is resolved by **dropping the stash** (GitBundle:447) | **Verified in the codebase 2026-10-06**: `Dialog::Stash`'s `Pop latest` dispatches `Operation::custom("Stash pop", …, v.stash_pop(root, 0))` (`crates/turbogit-ui/src/ui/dialogs.rs:1063-1071`); the CLI executor runs `git stash pop stash@{N}` and maps failure to `TgError` (`crates/turbogit-engine/src/cli.rs:1463-1468`), so a conflict surfaces through the standard error path with no message naming the surviving stash (git itself keeps the entry on a conflicted pop) | Copying this literally would teach users to delete their only copy. TurboGit must instead name the stash as still-needed. **Open divergence to resolve deliberately**, not copy. |
| UX | Shelf location is relocatable, including into a separate repository to share shelves with a team (shelving:231-237) | Not implemented | **Open gap**, low cost, and the "share shelves via a repo" rationale is worth preserving in whatever form. |
| UI | Silent shelving derives the shelf name from the changelist, explicitly risking collisions (`Default`, …) (shelving:170-171) | `Dialog::Shelve` asks for a name | TurboGit's explicit name is better: a silent path is the only place a derived name is acceptable, and the reference only reaches for it because it has no dialog. Not copied. |
| UX | Drag-and-drop between tabs, with a `⌃` modifier switching copy from move, and a one-second activation delay (shelving:171, 192) | No drag-reorderable changelists (`DISTILL.md` §"match intent") | **Match intent, record the divergence.** Same items and same order reachable by menu; the drag gesture and its `⌃` copy semantics are not reproduced. The one-second delay in particular should not be copied, it is an implementation artifact of a hover-activated tab. |
| UX | Apply vs Pop disambiguated by tooltip only (VcsBundle:1295) | `Apply` / `Pop` with distinct labels | No divergence; noted because the tooltip is the *only* place the
keep/remove consequence is spelled out, which is a discoverability trap worth
avoiding. |

## Needs runtime capture

1. **The Shelve dialog's region proportions and toolbar order**, the doc lists
   controls but not their arrangement (shelving:41-168 is a flat item table).
2. **Whether shelf `Delete` and stash `Drop`/`Clear` really have no confirmation.**
   The docs describe the menu path only; a confirmation dialog could exist and be
   simply unmentioned. **This is the highest-value capture on this surface** because
   the answer decides whether TurboGit's confirming stance is a divergence or a
   match.
3. **The `Already Unshelved` / `Restore` node's exact shape**, whether it is a

4. **Focus targets after shelf Delete, stash Drop, and stash Clear.**
5. **The merged Stash+Shelf tab's row grammar**, how a shelf and a stash are
   distinguished in one list (icon, prefix, or grouping), which the merged empty
   states (VcsBundle:1288-1291) imply but do not describe.
6. **Whether the `Clean working tree using` default is genuinely Shelve or Stash**,
   the settings tree lists both values with no default marker, and the smart-operation
   templates (GitBundle:426-429) cover both.
